# PRACTICAL LAB – Experiment 5: Token Economics
## Cost and Rate-Limit Budgeting Before Building an LLM Feature

---

## 1. Problem Statement
Before implementing an LLM-powered feature, developers must estimate how many tokens it may consume, what the expected API cost will be, and whether expected traffic fits within provider rate limits (RPM and TPM). This lab implements a pre-build budget planner that accepts feature assumptions, computes estimated token usage and costs, checks RPM and TPM limits with a configurable safety margin, and reports a go/no-go recommendation for the proposed feature.

---

## 2. Learning Objectives
- Understand input tokens, output tokens, total tokens, requests per minute (RPM), and tokens per minute (TPM).
- Estimate per-request, daily, and monthly token consumption before implementation.
- Calculate hosted API cost using configurable input and output token rates.
- Check expected traffic against RPM and TPM limits with a safety margin.
- Set per-request, daily, and monthly budget thresholds and identify risky assumptions.
- Use a modular Python program and unit tests to produce an automated pre-build budget report.

---

## 3. Key Concepts & Definitions

| Term | Meaning |
| :--- | :--- |
| **Input tokens** | Tokens sent to the model: system instructions, user prompt, conversation history, retrieved context (RAG), and function/tool descriptions. |
| **Output tokens** | Tokens generated by the model in its response. Typically priced significantly higher than input tokens. |
| **Total tokens** | Sum of input tokens + output tokens for a request. |
| **RPM (Requests Per Minute)** | Maximum number of API requests allowed per minute by the provider or tier. |
| **TPM (Tokens Per Minute)** | Maximum number of tokens allowed to be processed per minute across incoming requests and responses. |
| **Token Price** | Price per 1,000,000 input or output tokens for the selected model and tier. |
| **Safety Margin** | Additional capacity buffer (e.g., 20%) reserved for traffic spikes, estimation error, retries, and burst workloads. |

> **Important Distinction:** A cost estimate answers *"How much might this usage cost?"* while a rate-limit check answers *"Can the provider serve this traffic at the expected rate?"* A feature can be financially affordable but exceed RPM/TPM limits, or fit comfortably within rate limits but exceed the monthly budget.

---

## 4. Cost and Capacity Formulas

Let:
- $R$ = Expected requests per day
- $I$ = Average input tokens per request
- $O$ = Average output tokens per request
- $P_i$ = Input price per 1,000,000 tokens (USD)
- $P_o$ = Output price per 1,000,000 tokens (USD)
- $M_{pct}$ = Safety margin percentage (e.g., $20\% \implies \text{margin multiplier } M = 1 + \frac{20}{100} = 1.20$)

$$\text{Input Tokens/Day} = R \times I$$
$$\text{Output Tokens/Day} = R \times O$$
$$\text{Total Tokens/Day} = R \times (I + O)$$
$$\text{Daily Cost (USD)} = \frac{(R \times I \times P_i) + (R \times O \times P_o)}{1,000,000}$$
$$\text{Monthly Cost (USD, 30 days)} = \text{Daily Cost} \times 30$$
$$\text{Peak RPM (with margin)} = \text{Peak Requests/Minute} \times M$$
$$\text{Peak Total TPM (with margin)} = \text{Peak Requests/Minute} \times (I + O) \times M$$

## 10. Viva & Practice Questions

### Q1. What is the fundamental difference between RPM and TPM?
**Answer:** RPM (Requests Per Minute) limits the absolute number of network calls or transactions submitted to an API in any 60-second window, irrespective of request size. TPM (Tokens Per Minute) measures the total volume of input and generated output tokens processed across all requests in that same window. A single massive request can exhaust the TPM quota while consuming only 1 RPM.

### Q2. Why do LLM providers price output tokens higher than input tokens?
**Answer:** Generating output tokens requires auto-regressive decoding, where each token is computed sequentially in a separate forward pass conditioned on all previous tokens. In contrast, input tokens are processed simultaneously in parallel using vectorized matrix operations during prompt pre-fill. Hence, output generation ties up GPU memory bandwidth and compute resources for significantly longer durations.

### Q3. Why should a safety margin be included in token economics planning?
**Answer:** Real-world traffic deviates from average estimates due to user activity spikes, retry mechanisms on transient network failures, varied user prompt lengths, multi-turn conversation growth, and occasional verbose hallucinations. A safety margin (typically $15\%\text{--}30\%$) ensures that budget and quota limits are not breached under peak or non-ideal operating conditions.

### Q4. How does context caching affect token economics?
**Answer:** Context caching allows developers to pre-compute and store the key-value (KV) attention states of large, static prompt components (such as system guidelines, document libraries, or API schemas). Subsequent calls reuse these cached states, slashing input token pricing by $50\%\text{--}80\%$ and significantly reducing time-to-first-token (TTFT).

### Q5. What happens when an LLM application exceeds provider TPM or RPM limits?
**Answer:** The provider returns HTTP status code `429 Too Many Requests`. Unless the client implements robust exponential backoff, jitter, and queuing, requests will fail, leading to degraded user experience or complete feature outages.
